# 吉客云货品档案导入模板规范 v1

最近校对：2026-05-16（v3 — 主条码降级为可选；与 Phase0 命名口径对齐）
配套蓝图：`DOC/costing/blueprints/jackyun_erp_goods_master_sync_backlog.md`

> 本文是**给操作员**用的：照这个清单去吉客云后台导出全量货品 Excel/CSV，导出后交给系统做一次性快照。
>
> 数据规模预计 40 万行；后续日常增量走 API（`erp.storage.goodslist`），本模板仅用于首次盘点。

## 0. 操作要点

1. 在吉客云后台货品列表页找"批量导出"或"全部导出"。
2. 字段集按吉客云能勾出来的范围导即可，**不要求**包含本文 §2 列出的全部 40 列。
3. 单文件 ≤ 50 万行；如吉客云后台限单次行数，分多文件导出，文件名用 `goods_export_part1.xlsx` / `part2.xlsx` 等约定。
4. 文件编码：UTF-8 / Excel xlsx 均可。
5. 导出完成后放 `DOC/基础表单/`，文件名建议 `货品全量导出_YYYYMMDD.xlsx`。
6. 不要预先简化字段、不要预先去重、不要修改表头——系统这边按本文规范识别。

> **2026-05-16 用户实测订正**：吉客云后台货品档案导出 Excel 实测：
>
> - **`外部编码 outSkuCode`** —— 字段在（列名"外部编码"），但**值 100% 为空**，需靠 F 阶段 API 拉

> - **`停用`** —— ✅ 后台导出**有**这列（值用中文 `否` / `是`，非 `0/1`）
> - **`是否删除`** —— 后台导出没有，靠 API
>
> 所以这次 Excel 导入：
>

> - `外部编码` 列虽全空但要保留，给 F 阶段反查用
> - `停用` 列直接用，导入器按中文 `否/是` → bool 处理
> - 反写线（G1 Excel 反写）**必须等 API 同步至少跑过一轮**才能启动

## 3. 自定义字段（建议导但不强制）

### 3.1 货品自定义字段 1-50（`goodsField1-50`）

吉客云 ERP 实际启用的列数取决于客户配置。**建议导出全部 50 列**，列名用 `货品自定义字段1`、`货品自定义字段2`、…… `货品自定义字段50`。

落地：`metadata.erp.goods_field.{1,2,...,50}`，空值不存。

### 3.2 规格自定义字段 1-30（`skuField1-30`）

同上。列名 `规格自定义字段1` … `规格自定义字段30`。

落地：`metadata.erp.sku_field.{1,2,...,30}`。

### 3.3 扩展字段（`extendValue`）

吉客云另一套自定义字段，列名形如 `extend835999132354228992`，值在 `extendValue` JSON 字符串里。如果后台导出能直接展开成多列就直接导；如果只是一列 JSON 字符串，按原样导，系统会解析。

落地：`metadata.erp.extend.{extend...}`。

## 5A. 字段语义对齐（重要 — 三套叫法对照 + Phase0 旧规范对齐）

下表是为了让你在吉客云后台导出时认得出"勾的是不是同一个东西"。完整对齐表见
`DOC/costing/blueprints/jackyun_erp_goods_master_sync_backlog.md` §12 和 §15。

| 概念 | 吉客云 ERP 后台显示名 | 天猫 / 网店叫 | 我们系统内部叫 | 唯一性 |
|---|---|---|---|---|
| SKU 唯一识别码 | **条码 barcode** | — | `erp_sku_barcode` | 不可重复 |
| 69 码 / UDI（业务不用） | 主条码 mainBarcode | — | `metadata.erp.main_barcode` | 可重复 |
| 商家自定义编码 | **外部编码 outSkuCode** | **商家编码** | **`shop_spec_code`**（Phase0 沿用） | 一对一 SKU |
| 可执行工艺说明（系统侧源） | — | — | **`production_process`**（Phase0 沿用，升 L2） | — |
| 工艺说明(规)（ERP 镜像/反写落点） | 工艺说明(规) | — | `metadata.erp.process_instructions_reg` | — |
| 货品编号（SPU 级） | 货品编号 goodsNo | — | `product_code` | 一对一 SPU |
| 内部货品 ID | 货品ID goodsId | — | `erp_goods_id` | 一对一 SPU |
| 内部规格 ID | 规格ID skuId | — | `erp_sku_id` | 一对一 SKU |

**关键命名规则（v3，2026-05-16 修订）**：
- 网店"商家编码 / 模型编码"在系统内 **统一叫 `shop_spec_code`**（Phase0 起沿用，全链路用了一年）
- 系统生成的"工艺说明" **统一叫 `production_process`**（Phase0 起沿用）
- `shop_spec_code` 与 `production_process` 都从 metadata 升级为 `sku_master` 物理列，但**沿用旧名，不重新造名**
- 导入列 `外部编码/outSkuCode` 是 ERP 当前值，落 `out_sku_code`；它应该与系统规范值 `shop_spec_code` 对齐，反写成功后两者相同
- ERP 同步下来的 `工艺说明(规)` 只能落 `metadata.erp.process_instructions_reg`，**不要**反灌覆盖 `production_process`

**特别说明（用户 2026-05-16 口述）**：发货记录里有时会出现"商品编码+规格编码合在一起"的形式
（如 `Q26041801KB8-001`，前 9 位是 `Q26041801` 货品编号，后面是 `KB8-001` 模型变体码）。
我们系统的发货 mapper 已经在 `_normalize_shop_spec_code` 里识别并剥离前缀，落库后是干净的
`KB8-001`，原始值保留在 `metadata.shop_spec_code_raw` 给运营审计。导入 ERP 货品档案时
**不需要做这个拆分**，按吉客云导出的原值导即可。

## 6. 与现有 SKU 主档导入器的区别（避免误操作）

系统里**已经有一个** `POST /api/planner/sku-master/import` 接口，但它的表头是另一个版本：

```
货品条码（系统）、平台商品Id（网店）、平台规格Id（网店）、
销售渠道、商品名称（网店）、商品编码（网店）、商品规格（网店）、
货品规格（系统）、规格编码（网店）、匹配状态、匹配方式、
最后更新时间、生产工艺、规格图片（网店）、商品图片（网店）
```

这是**网店运营导出口径**，跟吉客云 ERP 货品档案是**两套数据**。

吉客云口径将来通过新接口落地（计划路径 `POST /api/planner/sku-master/import-jackyun`），**不要尝试用旧接口导本文规范的文件**，会因为缺"货品条码（系统）"列直接报错。
