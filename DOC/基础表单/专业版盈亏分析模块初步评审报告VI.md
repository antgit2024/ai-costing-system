# 专业版盈亏分析模块初步评审报告

**作者：Manus AI**  
**评审对象：** `phase0_review_checklist.md`、`finance_analyzer_integration_v1.md`、`sku_portfolio_management_v1.md`、`transfer_pricing_handbook.md`、`price_calculation_guide.md`、`pnl_analytics_module_design.md`  
**评审日期：2026-05-09**

## 一、总评结论

我先给一个明确判断：这套方案的**大方向是对的**，已经不是普通“成本公式表”，而是往专业 ERP 管理会计体系靠近了。它抓住了你们当前最核心的矛盾：你们不是传统批量制造，而是接近 POD 的订单式、小批量、多材质、多 SKU、快速发货模式，所以不能用单一标准成本直接压给运营，也不能只看集团总利润。方案里提出的**价格分层、发货级利润宽表、工厂与运营内部转移价、SKU 组合管理、月度财务反推校准**，这些方向都是正确的。

但是，这个方案目前还存在一个明显问题：它已经设计得很“完整”，但有点偏“大而全”。如果直接按 Phase 1 到 Phase 5 全量开发，会周期长、口径多、上线慢，而且最危险的是：系统上线后可能还没有解决老板最关心的问题——**今天发出去的订单到底赚不赚钱，亏在哪里，哪些 SKU 要砍，哪些成本能马上优化**。

因此，我的初步评审结论是：**方案可以立项，但必须压缩成一个“先算清楚钱”的 MVP 版本**。第一阶段不要先追求 AI、店铺组合、复杂工作流，而要先把“发货明细利润事实表 + 成本快照 + 月度对账 + 亏损清单”做出来。只要这四件事跑通，你们马上就能看出哪些产品亏钱、亏多少钱、亏在材料、人工、制造费、运费、平台费、广告费还是售价太低。

| 评审维度 | 初步判断 | 说明 |
|---|---:|---|
| 战略方向 | 高度正确 | 已经从“成本计算器”升级为“经营利润分析系统”。 |
| 成本分层 | 正确但需收敛 | 真实成本、工厂全成本、转移价、销售底价需要保留，但第一阶段必须优先服务发货利润核算。 |
| POD 适配度 | 较高 | 已考虑多材质、多 SKU、发货确认成本、幅宽损耗和订单式生产。 |
| 落地难度 | 偏高 | 当前模块太多，建议先做利润事实表和成本差异分析。 |
| 财务严谨性 | 中高 | 内部转移价、月度对账、集团抵消方向正确，但固定成本、异常成本、税务公允性还要细化。 |
| 经营可用性 | 需要增强 | 需要增加“亏损处理决策规则”和“成本优化归因模块”，否则只是报表，不是决策系统。 |

## 二、方案最值得保留的核心设计

第一，方案已经正确区分了不同价格口径。原来最大的问题是把“工厂全成本”直接当成运营采购成本，导致运营认为价格无法销售。现在文档中把**变动成本、工厂全成本、内部转移价、批发价下限、零售建议价下限**拆开，这是专业管理会计中非常关键的一步。尤其是工厂与运营是两个独立公司时，必须既能算集团合并利润，也能让工厂和运营分别独立核算。

| 价格/成本口径 | 正确用途 | 初评意见 |
|---|---|---|
| 变动成本 | 判断大促、清仓、引流是否还能做 | 必须保留，而且要作为“绝对亏损底线”。 |
| 工厂全成本 | 工厂内部考核与效率管理 | 必须保留，但不能直接压给运营作为市场销售依据。 |
| 内部转移价 | 工厂卖给运营的结算价 | 必须保留，但要增加市场价格锚定和特批机制。 |
| 批发价下限 | B 端报价底线 | 可以保留，但第一阶段优先级低于零售实收利润分析。 |
| 零售建议价下限 | 店铺定价和活动底价 | 必须保留，但要接入实际售价、广告费、退款和平台扣点。 |

第二，方案提出用**发货级利润宽表**作为分析核心，这是非常正确的。你们的成本不是生产完批量入库再平均分摊，而是发货才确认成本。真正能指导经营的不是 SKU 主数据里的理论成本，而是每一条发货记录对应的实际售价、成本快照、平台费用、运费、退款售后和毛利。只要 `shipment_pnl_lines` 做对，后面的 SKU 亏损榜、材质对比、店铺利润、工厂对账、AI 分析都可以建立在它上面。

第三，方案用**原料幅宽下料面积**替代产品面积，这一点特别适合你们的问题。你提到 120cm 的料做 70cm 和 90cm 产品，实际成本差不多，但如果按产品平方算，70cm 会被算得过低，结果小规格越卖越亏。文档中的 `area_with_cutting` 方向是对的，不过后面还要升级成更真实的“排版占用面积”，这点我在风险部分会详细说明。

第四，SKU 组合管理的思路是对的。不是所有亏损 SKU 都要砍，因为有些 SKU 是引流款、形象款、动销款。亏损治理必须结合 SKU 角色，否则会把店铺流量入口砍掉。但是第一阶段不要把组合模型做得太复杂，先建立“亏损 SKU 是否属于引流/利润/形象/测试”的最小标签即可。

## 三、目前方案最大的五个风险

### 1. 现在的系统目标太大，第一阶段容易做散

`pnl_analytics_module_design.md` 已经包含财务集成、成本引擎、发货宽表、SKU 组合、店铺矩阵、AI 周报、自然语言问答、下架工作流、调价工作流等内容。这个蓝图完整，但如果马上全做，会导致开发周期过长，而且大量功能在真实成本口径没跑稳之前没有意义。

我的建议是把第一阶段目标压缩为一句话：**让老板每天能看到昨天发出去的订单，按店铺、产品、材质、尺寸、SKU 分别赚了多少钱、亏了多少钱、亏在哪里。**

| 当前设计 | 初评问题 | 建议处理 |
|---|---|---|
| Phase 1 到 Phase 5 很完整 | 容易开发周期长、上线慢 | 先做“利润事实表 MVP”。 |
| AI 周报、自然语言问答 | 成本口径未稳定前输出容易误导 | 放到第三阶段以后。 |
| 店铺组合工作台 | 有价值，但依赖利润事实表 | 等发货利润跑通后再做。 |
| 下架/调价工作流 | 是最终形态，不是第一步 | 第一阶段先输出建议，不自动执行。 |

### 2. “真实成本”不能只靠标准成本，还必须有成本快照和月度差异

文档中已经说明 v2 是“半实际成本”，平时用标准成本运转，月底从财务数据反推校准。这个方向是现实可行的，因为你们 SKU 过百万、订单小批量，不可能每单都做复杂实际领料核算。但是，系统展示时必须把它说清楚：第一阶段算出的不是会计意义上的完全实际成本，而是**发货时点的标准经营成本 + 月度实际差异校准**。

这里必须增加两个关键机制。第一，每条发货记录必须锁定一个**成本快照**，包括当时的物料单价、人工单价、制造费率、损耗算法、版本号和计算时间。否则以后物料价格改了，历史利润会被重算得面目全非。第二，月底财务实际数出来以后，要做**标准成本与实际成本差异分摊**，区分物料价差、用量差、人工效率差、制造费差和异常损耗。

| 必须字段 | 作用 | 是否应第一阶段实现 |
|---|---|---:|
| cost_snapshot_id | 锁定发货时点成本版本 | 是 |
| material_price_version | 记录当时材料单价来源 | 是 |
| labor_rate_version | 记录当时人工单价来源 | 是 |
| overhead_rate_version | 记录当时制造费率 | 是 |
| costing_method | 记录按面积、按幅宽、按件、手工覆盖等算法 | 是 |
| data_quality_tag | 标记成本缺失、售价缺失、运费缺失等问题 | 是 |
| monthly_variance_allocated | 月底实际差异分摊金额 | 第二阶段实现 |

### 3. 固定制造费用不能直接决定砍不砍 SKU

你们现在要“亏钱的就砍掉”，这个方向对，但要非常小心。财务上必须区分**贡献毛利亏损**和**全成本分摊后亏损**。如果一个 SKU 的售价连材料、人工、包装、运费、平台费都覆盖不了，那是真亏，应该优先砍或涨价。如果一个 SKU 变动成本能覆盖，但加上固定制造费分摊后亏损，那不能简单砍掉，因为砍掉它以后，房租、设备折旧、管理人员工资这些固定费用并不会马上消失，反而可能分摊到剩下 SKU 上，让其他产品看起来更贵。

因此，盈亏模块必须至少输出三层利润，而不是只输出一个“净利润”。

| 利润层级 | 公式方向 | 经营含义 | 决策用途 |
|---|---|---|---|
| 贡献毛利一 | 实收收入 - 材料 - 直接人工 - 包装 - 运费 - 平台直接扣点 | 订单本身是否越卖越亏 | 低于 0 的 SKU 优先砍或涨价。 |
| 经营毛利二 | 贡献毛利一 - 广告费 - 退款售后预提 | 店铺经营动作后是否赚钱 | 判断活动、投放、售价是否合理。 |
| 全成本利润三 | 经营毛利二 - 固定制造费分摊 - 管理费用分摊 | 会计全口径盈亏 | 用于月度复盘，不应单独作为砍 SKU 唯一依据。 |

### 4. 幅宽损耗公式方向正确，但还不够真实

文档中 `area_with_cutting` 使用“有效宽 = ceil(产品宽 / 原料宽) × 原料宽，实际消耗面积 = 有效宽 × 产品长”的方式，能解决 120cm 幅宽做 70cm 产品低估成本的问题。这是第一版必须做的。但从生产真实情况看，还需要进一步考虑**旋转、拼版、同日订单合并排版、边角料回用、卷头卷尾损耗、瑕疵损耗**。

如果第一阶段只用简单公式，建议命名为“标准下料占用面积”，不要直接叫“实际消耗面积”。真正准确的应该是来自生产排版或裁切记录的“实际占用面积”。

| 损耗因素 | 当前方案覆盖情况 | 建议 |
|---|---|---|
| 原料幅宽差异 | 已覆盖 | 保留。 |
| 70/90/110 不同规格的幅宽损耗 | 已初步覆盖 | 保留。 |
| 产品可旋转排版 | 未充分覆盖 | 增加 `allow_rotate` 参数。 |
| 同材质多订单合并裁切 | 未覆盖 | 第二阶段增加“日批次排版池”。 |
| 边角料回用 | 简化覆盖 | 第一阶段可先按价值率冲减，后续接库存。 |
| 卷头卷尾、瑕疵、返工 | 未充分覆盖 | 先做月度差异分摊，不要强行到单件。 |

### 5. 内部转移价不能只按“全成本 × 利润率”，必须加市场锚定

内部转移价手册的方向是正确的，但要注意你们是两个独立公司，工厂给运营开票时既要能让工厂有合理利润，又不能让运营拿到一个远高于市场的采购价。文档中已经提到关联交易公允性，这是对的。但在实际落地中，转移价必须同时受三条线约束：**成本线、市场线、税务线**。

如果成本算出来很高，而同行进货价明显更低，不能机械地按全成本加利润率给运营。否则系统会告诉运营“你应该卖很贵”，但市场根本不接受。正确做法是把差额暴露出来：如果内部转移价高于市场批发价，系统应标记为**工厂成本竞争力不足**，而不是让运营背锅。

| 转移价约束 | 说明 | 建议规则 |
|---|---|---|
| 成本线 | 工厂至少要知道自己的全成本 | 用于工厂效率考核。 |
| 市场线 | 同行批发/进货价是外部竞争锚点 | 内部转移价高于市场价时报警。 |
| 税务线 | 两公司关联交易要符合公允性 | 建议保留市场询价记录。 |
| 战略线 | 引流、清仓、爆款可能低于转移价 | 必须走特批和单独补贴账。 |

## 四、我建议的“专业版分析模块”最小闭环

结合你现在的诉求，我建议第一阶段不要叫“AI 盈亏分析系统”，而是先做成**订单利润作战室**。它的底层只有一个核心：发货利润事实表。所有经营分析都从这张表出来。

> 第一阶段目标：每一条发货数据进来后，系统自动计算该订单的标准成本、实际实收、订单毛利、亏损原因标签，并汇总出按 SKU、产品模型、材质、尺寸、店铺、工厂、平台的赚钱榜和亏钱榜。

### 4.1 必须优先建设的四张表

| 表名 | 定位 | 关键作用 |
|---|---|---|
| `shipment_profit_fact` | 发货利润事实表 | 一条发货明细一条利润记录，是所有分析的底座。 |
| `shipment_cost_snapshot` | 发货成本快照表 | 锁定每单当时的物料、人工、制造费、损耗算法和版本。 |
| `monthly_cost_variance` | 月度成本差异表 | 月底把标准成本与财务实际成本差异拆出来。 |
| `sku_decision_board` | SKU 决策看板表 | 输出保留、涨价、优化、下架、观察等建议。 |

### 4.2 发货利润事实表建议字段

这张表必须能够回答一个问题：**这一单到底赚了多少钱？**字段不宜过少，否则后期无法解释亏损原因。

| 字段组 | 建议字段 | 说明 |
|---|---|---|
| 交易信息 | 发货单号、订单号、平台、店铺、SKU、产品模型、材质、尺寸、数量、发货日期 | 用于多维汇总。 |
| 收入信息 | 原价、实际成交价、优惠金额、买家实付、运费收入、退款金额、净收入 | 必须用实际销售价格，不用挂牌价。 |
| 成本信息 | 主材成本、辅料成本、包装成本、直接人工、变动制造费、固定制造费分摊 | 成本必须拆开。 |
| 运营费用 | 平台扣点、支付手续费、广告费分摊、佣金、运费险、售后预提 | 用来判断运营动作是否亏损。 |
| 利润结果 | 贡献毛利一、经营毛利二、全成本利润三、毛利率、亏损标签 | 用于经营决策。 |
| 版本追溯 | 成本快照ID、价格参数版本、数据质量标签、是否手工覆盖 | 保证历史数据可解释。 |

### 4.3 决策规则建议

亏损 SKU 不能只按一个利润率判断，必须分层处理。建议第一阶段就内置一套简单、透明、可人工复核的规则。

| 分类 | 判断逻辑 | 建议动作 |
|---|---|---|
| 真亏损 SKU | 近 30/60/90 天贡献毛利一为负，且销量达到最低样本量 | 立即涨价、替换材料、优化工艺或下架。 |
| 运营亏损 SKU | 贡献毛利一为正，但经营毛利二为负 | 检查广告费、平台活动、退款、运费补贴。 |
| 全成本亏损 SKU | 经营毛利二为正，但全成本利润三为负 | 不直接下架，先看固定费用分摊和产能利用率。 |
| 引流亏损 SKU | 亏损但带来关联销售或店铺流量 | 设置亏损预算池，不能无限亏。 |
| 数据异常 SKU | 售价、成本、运费、退款或材质缺失 | 不进入下架决策，先修数据。 |

## 五、成本优化模块应补充的内容

你现在不仅要知道谁亏钱，还要知道成本哪里能优化。当前方案里有物料集采建议、同尺寸物料对比，这是好的，但还不够。专业版应该有一个**成本差异归因模块**，它专门解释“为什么这个月比上个月贵了”。

| 成本优化方向 | 分析问题 | 可输出建议 |
|---|---|---|
| 材料价格差异 | 同材质采购单价是否上涨？不同供应商是否有差价？ | 集采、换供应商、锁价、替代材料。 |
| 材料用量差异 | 实际幅宽损耗是否高于标准？小规格是否亏损？ | 调整规格价格、优化排版、合并裁切。 |
| 人工效率差异 | 单件工时是否过高？哪个工序拖慢？ | 工艺模板、计件工资、工序合并、员工培训。 |
| 制造费差异 | 水电、租金、设备、管理费用是否异常？ | 区分固定费用和异常费用，不能全部压给 SKU。 |
| 运费包装差异 | 哪些尺寸、地区、店铺运费亏？ | 运费模板调整、包装规格优化、偏远地区加价。 |
| 售后退款差异 | 哪些材质或尺寸退货率高？ | 优化详情页、质检、停卖高退货材质。 |
| 广告投放差异 | 是否广告吃掉利润？ | 限制亏损 SKU 投放，按 SKU ROI 调整预算。 |

我建议成本优化模块至少输出一张“成本优化机会榜”。不是只列亏损 SKU，而是按“可节省金额”排序。例如：某材质本月消耗 3000㎡，采购单价比替代供应商贵 1.2元/㎡，理论节省 3600元；某规格因幅宽损耗导致每件多耗 0.35㎡，本月卖 1000件，理论损耗成本 6000元。这种榜单比单纯毛利率更有行动价值。

## 六、对现有六份文档的逐项初评

| 文档 | 初评结论 | 需要修改的重点 |
|---|---|---|

## 七、建议的落地顺序

我建议你们按“先算清楚，再做优化，再上 AI”的顺序落地。现在最重要的是不要被大系统拖慢。

| 阶段 | 时间建议 | 核心目标 | 必须产出 |
|---|---|---|---|
| 第 0 阶段 | 3-5 天 | 统一口径 | 成本字段定义、费用科目映射、利润层级定义、数据质量规则。 |
| 第 1 阶段 | 2-3 周 | 算清每单利润 | 发货利润事实表、成本快照、SKU 赚钱榜/亏钱榜、店铺利润表。 |
| 第 2 阶段 | 2-3 周 | 找出亏损原因 | 成本差异归因、材料/人工/制造费/运费/退款/广告拆解。 |
| 第 3 阶段 | 2 周 | 形成经营动作 | SKU 决策看板、涨价建议、下架建议、材料替代建议。 |
| 第 4 阶段 | 后置 | AI 辅助分析 | AI 周报、自然语言问答、自动诊断。 |

## 八、我建议你下一步重点细看这五个问题

第一，你要确认系统第一阶段到底按什么利润口径判断“亏钱”。我的建议是：**砍 SKU 优先看贡献毛利一，不要直接看全成本利润三**。贡献毛利一为负，说明订单越卖越亏；全成本利润为负，可能只是固定费用分摊问题。

第二，你要确认每条发货数据能否拿到真实实收金额。挂牌价没有意义，必须拿到订单实付、优惠、平台扣点、退款、运费收入和售后成本。如果没有这些，系统只能算理论利润，不能算真实经营利润。

第三，你要确认成本快照能不能锁住。物料价格、人工费率、制造费率、损耗规则都必须按发货时点锁定版本。否则历史数据会随着今天的成本参数变化而变化。

第四，你要确认幅宽损耗第一版怎么取舍。第一版可以用标准公式，但要承认它是“标准占用面积”，不是绝对实际耗料。等生产端有裁切/排版记录后，再升级成真实消耗。

第五，你要确认内部转移价是否引入市场价对标。如果你们工厂全成本高于同行批发价，系统不能简单把高成本传给运营，而要暴露为“工厂成本竞争力问题”。这对现在行业下滑、每一分钱都要抠的情况非常关键。

## 九、最终建议

我的建议是：这套方案**可以继续推进，但要立刻收敛成“专业版盈亏分析 MVP”**。第一阶段不要追求全功能，而要把以下四件事情做透：

| 第一阶段必须做透 | 目标 |
|---|---|
| 发货利润事实表 | 每单发货都能算出收入、成本和利润。 |
| 成本快照 | 每单成本可追溯，不被后续改价污染。 |
| 多层利润 | 区分贡献毛利、经营毛利、全成本利润，避免误砍 SKU。 |
| 亏损原因标签 | 能看出亏在售价、材料、人工、损耗、运费、平台费、广告费还是退款。 |

只要这四件事跑通，你们就能开始做真正的经营动作：亏损 SKU 涨价或下架，材料贵的做集采，人工高的改工艺，幅宽损耗高的调整规格价格，广告吃利润的停投，退货高的停卖或改详情页。后面的 SKU 组合、AI 周报、自动调价、下架流程都可以逐步加，但不能反过来先做这些“漂亮功能”。

**一句话结论：现有方案方向对，但要从“大而全的系统蓝图”改成“先把每一单赚亏算清楚的经营作战系统”。**
