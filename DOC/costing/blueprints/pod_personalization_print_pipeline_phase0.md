# POD 个性化定制（先印布）— Phase0 落地蓝图（以抱枕为例）

> 目标：用户上传图片 → 选择标准模型（抱枕）→ 在线排版预览（效果图）→ 确稿 → 后端生成**印刷稿（print-ready）** → 工厂下载生产 → 系统回传 ERP（订单处理结果/生产包链接/追溯ID）。
>
> 约束（本 Phase0 明确）：
> - **先不引入 AI/ComfyUI**（可在 Phase1 作为“效果图增强”加入）
> - **先印布，再裁剪缝制**（必须有“裁片模板/出血/安全区/缝边吃进”的确定性参数）
> - 工厂要求：**需要裁切线/定位标**（颜色管理 CMYK/ICC 也要预留）
> - 交付给 ERP：以 **API 回传**为主（本系统是“订单大脑”，生成生产包后把结果回写 ERP）

---

## 1. 关键理念：把“设计稿”也做成快照（像 BOM 快照一样）

你们当前主线是“发货时再解析 → BOM 快照/异常队列 → 可重试/可追溯”。  
POD 链路必须沿用同一哲学：**确稿后产生不可变的“设计稿快照（Artwork Snapshot）/印刷稿快照（Print Snapshot）”**，并与订单行、模型版本、规格解析结果强关联。

### 为什么必须快照
- 模型/模板参数变更不能回写历史订单
- 同一张图重复下单要可复用（hash 去重）
- 工厂重下/重打/补发必须可重跑、可追溯

## 2. Phase0 里要新增/固化的对象（最小）

> 名称是建议口径；你们可以落在新表或 metadata_json，但**字段语义要固定**。

### 2.1 ArtworkAsset（用户素材）
- `id`
- `source`: upload / url / erp_attachment
- `file_url` / `storage_key`
- `sha256`（去重）
- `width_px` / `height_px` / `dpi_estimate`
- `license_confirmed`（用户确认）
- `status`: active/blocked（涉政涉黄等可选后置）

### 2.2 ProductMockupSpec（效果图模板定义，按模型版本）
> 用于“用户看到的效果图”，不等于印刷稿，但要与印刷模板一致（避免效果与生产不一致）。

- 关联：`product_model_version_id`（**必须锁版本**）
- `view`: front/back（抱枕至少正反）
- `mockup_base_image_url`（底图：室内场景/平铺图，可多套）
- `placement_polygon`（素材贴图区域：四点/多边形）
- `shadow/highlight`（可选：叠加层参数，Phase0 可不做）

### 2.3 PrintTemplate（印刷模板定义，按模型版本 & slot）
> 这是“先印布”场景的核心。

- 关联：`product_model_version_id` + `structure_slot`（如 `PILLOW_V1:front_panel`）
- `final_product_size_mm`（成品尺寸）
- `print_piece_size_mm`（印布裁片外框尺寸：含出血/缝边吃进）
- `safe_area_inset_mm`（安全区内缩）
- `bleed_mm`（出血）
- `seam_allowance_mm`（缝边/吃进）
- `cutline_path`（裁切线：SVG path / DXF / PDF 矢量层）
- `registration_marks`（定位标：位置/样式）
- `mirror_rule`（是否镜像/翻转）
- `color_profile`（ICC profile 名称或引用）
- `output_format_profile`（PDF/PNG/TIFF 的固定参数：色彩空间、分辨率、压缩）

### 2.4 ArtworkJob（生成任务：效果图/印刷稿）
- `job_id`
- `job_type`: mockup_render / print_export
- `input`: asset_id + template_id + transform（位置/缩放/旋转/裁剪）
- `output`: files[]（效果图/印刷稿）
- `workflow_version`（渲染算法/模板版本号，便于重跑）
- `status` + `error`

### 2.5 ProductionPack（生产包）
- `production_pack_id`
- `order_line_ref`（来自 ERP 的订单明细行唯一键）
- `product_model_version_id`
- `spec_text_normalized` + `spec_hash`（内部规范化后的规格口径）
- `print_files[]`（按 slot/view 分文件：front/back）
- `manufacturing_instructions_text`
- `bom_snapshot_ref`（或 `bom_snapshot_id`）
- `trace_ids`（串起全链路的追溯ID）
- `status`: ready/issued/cancelled

## 3. Phase0 端到端流程（建议）

### Step A：用户端（网站/H5/小程序）
1) 选品：选择“抱枕标准模型”（实际上选择一个可用的标准版本）
2) 选规格：尺寸（40×40、50×50、圆形直径等）
3) 上传图片：得到 `ArtworkAsset`
4) 在线编辑：裁剪/缩放/旋转/（可选加文字）
5) 生成效果图预览：`mockup_render` job → 产出 preview 图片
6) 确稿：提交“排版参数（transform）+ 选中的 print template”

### Step B：后端（确稿后不可变）
1) 写入 `ProductionPack`（ready）
2) 生成印刷稿：`print_export` job
3) 生成 BOM 快照（与该生产包绑定）：复用现有 `bom/generate` 能力
4) 回传 ERP：写回“生产包已就绪 + 下载链接 + 追溯ID +（可选）成本摘要”

### Step C：工厂端
1) 工厂登录/鉴权后下载 production pack（印刷稿 + 指令）
2) 工厂生产（先印布→裁剪→缝制→质检→出库）
3) 产线状态回传（可选 Phase1/2）：开工/完工/质检/出库/快递单号

## 4. 小程序接入可行性（Phase0 口径）

### 4.1 你的“本地服务器能否给小程序用”的关键前提
小程序客户端 **无法直接访问纯内网/局域网 IP**。要让小程序可用，你至少需要：
- **公网可达的 HTTPS 域名**（并完成小程序后台“合法域名”配置）
- 后端接口与文件下载域名都要在白名单内
- 上传图片一般走：小程序上传到你的对象存储（或你的后端中转），再由后端处理

结论（Phase0）：  
- **如果你说的“本地服务器”仅内网可访问 → 基本不可用**（除非走 VPN/专线/网关转发，不建议）。
- **如果你的本地服务器通过公网域名反代暴露（Nginx/网关）+ HTTPS + 鉴权 → 可用性很高**。

### 4.2 小程序实现建议（避免踩坑）
- 图片上传：
  - 推荐：直传对象存储（OSS/S3），后端拿 `storage_key` 拉取处理（省流量、省网关带宽）
  - 次选：上传到后端（对你们带宽/并发压力更大）
- 效果图/印刷稿生成：
  - 建议异步 job（避免小程序请求超时）
  - 小程序轮询 job 状态或用 Webhook/订阅消息（后置）
- 下载：
  - 工厂下载一般是 PC 浏览器/企业微信/钉钉，不建议在小程序里承载大文件下载

## 4.3 “最新 POD / 人人都设计师”模式（AI 介入点，建议 Phase1）

> 你描述的模式本质是：**AI 负责“生成/改造创意图”**，你们系统负责 **“把图变成可生产的印刷稿（print-ready）+ 可追溯生产包 + 回传 ERP”**。
>
> 关键原则：**AI 输出只能作为“素材”（RGB 图像）**；“裁片几何/出血/裁切线/定位标/镜像规则/尺寸标注/ICC”必须由确定性模板管控，不能交给 AI 猜。

### A) 现今常见 POD 形态（你可以对标）
- **模板化 POD（主流）**：用户在固定产品模板上放图/文字 → 系统生成效果图与印刷稿 → 工厂生产。
- **AI Assisted POD（你要的）**：
  - 文生图：Prompt → 生成主题风格图（节日、插画、潮牌、国风等）
  - 图生图/风格化：用户照片 → 指定风格（油画/动漫/水彩/复古海报）→ 输出新图
  - 补全/扩图：解决裁片比例与出血区（outpainting），减少“裁切掉头/手/主体”
  - 高清化/去噪：提升分辨率与细节（避免印刷糊）
- **UGC 生态型 POD（平台化）**：用户作品可发布/上架，别人也可下单生产（涉及版权/分润/审核体系）。

### B) 推荐把“AI 能力”落到你们系统里的 3 个位置（从稳到强）
1) **上传前/上传后素材增强（最低风险）**
   - 去背景、修复、高清化、扩图、自动构图建议
2) **生成“可用素材”（创意生产）**
   - 文生图/图生图生成 1~N 张候选图（用户挑选）
3) **效果图增强（可选）**
   - 用 AI 做更拟真场景图/布料褶皱，但最终印刷稿仍走确定性管线

### C) 从 AI 图到“印刷稿”的生产级护栏（必须，不然会翻车）
- **分辨率门槛（硬规则）**：
  - 以裁片尺寸与目标 DPI 推算所需像素；不足则禁止确稿或强制高清化
- **色彩管理（CMYK/ICC）**：
  - AI 通常输出 RGB（sRGB），生产前必须按工厂 ICC 做转换与打样口径
  - 不能“看着差不多”，要有可复现的 profile 与转换参数
- **几何与标记（确定性模板）**：
  - 出血/安全区/缝边吃进、裁切线、定位标、镜像规则必须来自 PrintTemplate
  - 任何“让 AI 自己画裁切线/标记”的做法都不可控
- **合规/版权（必须有策略）**：
  - 生成内容审核（涉政涉黄等）
  - 用户上传与 AI 生成的版权声明/授权勾选

### D) 自动拼版（可选，Phase2 更合适）
- 条件：同材质/同工艺/同色彩 profile/同布幅
- 产物：拼版 PDF/TIFF + 每单定位信息（便于裁剪/对单）
- 注意：拼版属于生产效率优化，不是 Phase0 必需项；先把单单可生产跑通

## 5. 现有系统如何最小复用（建议落点）

### 5.1 版本化与追溯
- **必须锁定**：`product_model_version_id`（确稿时绑定）
- 复用：`spec_hash`、BOM 快照、异常队列语义（确稿失败/生成失败同样应入队列可重试）

### 5.2 结构标准（抱枕）
建议沿用 `PILLOW_V1` 的 slot 口径，把印刷模板按 slot 管理：
- `front_panel`：正面印刷裁片
- `back_panel`：背面印刷裁片（如需要）
（其它 slot 如拉链位/侧边位不一定参与印刷，但可参与工艺与 BOM）

## 6. Phase0 的“验收定义”（建议一条龙）

给定 1 个标准模型版本（抱枕 40×40）+ 1 张用户图片：
1) 生成效果图成功（预览可下载）
2) 确稿后生成印刷稿成功（含裁切线/定位标）
3) 生成 BOM 快照成功（可查看扣库清单）
4) 生产包可下载（工厂侧拿到 print-ready 文件）
5) ERP 收到回传（至少包含 production_pack_id + 下载链接 + trace_id）

## 7. 大文件与性能：为什么“Web 跑不动”是对的，以及正确的架构

> 你担心的点非常真实：print-ready 文件（尤其 TIFF/高 DPI）会很大，**不应该**让浏览器承担“生成/拼版/导出”的重活。
>
> 正确做法是：**浏览器只做轻量编辑与预览**；真正的生产文件生成由后端异步 worker 完成，并落到对象存储给工厂下载。

### 7.1 浏览器（Web/H5/小程序）应该做什么
- 上传素材（最好直传对象存储，避免经过后端网关）
- 轻量编辑参数：裁剪框/缩放/旋转/对齐（只传参数，不在本地导出大文件）
- 看预览图：只看 **压缩预览 PNG/JPG/WebP**（例如最长边 2048px），用于确认构图

### 7.2 后端/Worker 必须做什么（生产级）
- 生成 print-ready（PDF/TIFF/PNG）与校验（DPI/ICC/标记层）
- 生成/保存 ProductionPack 快照与追溯信息
- 把产物落到对象存储（OSS/S3），并提供受控下载（短期签名 URL 或鉴权下载）

### 7.3 关键工程策略（Phase0 就该用）
- **对象存储作为大文件的 SSOT**：后端只保存 `storage_key + metadata`，不要把大文件塞数据库
- **异步任务**：生成印刷稿是 job（避免请求超时），前端轮询 job 状态
- **预览与生产分层**：
  - 预览：小图、快、可反复
  - 生产：大图、慢、只在“确稿”后生成一次并快照化
- **输出格式选择（现实建议）**：
  - 若工厂允许：优先 PDF（裁切线/定位标可做矢量层，文件通常更可控）
  - TIFF：尽量只在工厂硬要求时使用（体积大、传输慢、容易把 Web 拖死）

结论（Phase0）：  
只要你把“生成印刷稿”放在后端 worker 并用对象存储承载大文件，Web 端完全不需要“跑得动”大文件，仍然能完成在线定制与确稿闭环。

## 8. 自动拼版（Imposition）：后端能做，也可以独立“打印服务器”做（建议 Phase2）

> 你关心的重点是：很多订单的 PDF 能否自动拼版，减少人工、稳定且安全。
>
> 结论：**能做**。拼版属于典型“离线重计算/批处理”任务，非常适合后端 worker 或独立打印服务器。

### 8.1 两种部署形态（都可行）

#### A) 直接在你们后端的 Worker 做拼版（云/本机均可）
- 优点：系统一体化，追溯/权限/回传 ERP 更顺
- 适用：拼版规则相对标准（按布幅/边距/行列排版/固定间距），产能中等

#### B) 独立“打印服务器 / 拼版服务器”（推荐给你们：更稳、更安全）
- 形态：一台（或一组）专用服务器，只做：PDF 拼版 + RIP 前处理（可选）
- 优点：
  - 与业务系统隔离（安全域更清晰）
  - 大文件/高 CPU 任务不影响 Web API
  - 更贴合工厂网络环境（内网访问、权限更好管）
- 你们系统只要把任务投递过去，拿回产物即可

### 8.2 拼版的输入/输出（建议固定契约）

#### 输入（来自 ProductionPack 的“裁片PDF”）
- 多个订单的裁片文件（每个裁片都有：尺寸、出血、裁切线层、定位标层、镜像规则、ICC profile 标识）
- 拼版参数（工厂提供/你们固化）：
  - 布幅宽度（mm）、左右边距、上下边距
  - 裁片之间最小间距（mm）
  - 允许旋转（0/90）与镜像（通常镜像已在单裁片阶段处理）
  - 同批次约束：同面料/同工艺/同 ICC profile/同印花机参数

#### 输出
- `imposed_pdf`：一份拼版后的 PDF（或 TIFF，按工厂设备）
- `placement_map.json`：每个订单裁片在拼版中的位置/页码/坐标（便于对单、裁剪、返工重打）
- `imposition_report.json`：本次拼版使用了哪些输入、耗时、失败原因、浪费率估算（可选）

### 8.3 安全与稳定（你提到“最重要：安全、稳、省人工”）
- **访问控制**：
  - 工厂下载走受控链接（短期签名 URL）或工厂账号鉴权下载
  - 拼版服务器与业务系统建议走内网/VPN + mTLS（可选）
- **不可篡改与追溯**：
  - 拼版输出也要快照化：记录 input 文件 hash + 拼版参数 + 输出文件 hash
- **失败可重试**：
  - 拼版任务必须是 job（可重跑），失败原因要结构化（某裁片缺失/ICC 不一致/尺寸异常）

### 8.4 最小落地顺序（建议）
1) 先跑通“单单裁片 PDF”自动生成（Phase0）
2) 再做“按面料/工艺分组 → 一键拼版”（Phase2）
3) 最后再考虑更复杂的优化：自动套料/最小浪费率/多机台并行

### 8.5 已有 RIP + 切割设备时，如何做到“全自动下发打印机/切割机”

> 你确认了：你们**有 RIP 软件**、也**有切割设备**。这意味着可以实现“生产包就绪 → 自动进 RIP 队列 → 自动打印 → 自动对位切割”的闭环。
>
> 核心原则：你们系统不直接连打印机，而是连“工厂打印服务器（RIP 队列控制点）”。

#### 推荐链路（最稳、最省人工）
- 你们系统：生成 `ProductionPack`（裁片 PDF + 位置映射 + 追溯ID）
- 工厂打印服务器：
  - 拉取 ProductionPack（受控下载/内网访问）
  - 按布幅/机台/工艺规则进行拼版（imposed_pdf + placement_map）
  - 把拼版结果投递到 RIP（常见方式：热文件夹/队列 API/命令行）
- RIP：
  - 负责 ICC/网点/分色/设备参数（介质、模式、分辨率、走布速度等）
  - 输出到打印机队列
- 切割设备：
  - 读取同一张拼版上的**定位标 + 裁切线层**进行相机对位裁切

#### 你们系统与工厂侧要约定的“最小契约”
- **裁切线格式**：PDF 矢量层（常用）或单独 SVG/DXF（取决于切割设备）
- **定位标规范**：标记样式/尺寸/颜色/位置（必须固定）
- **RIP 接入方式**：热文件夹（最常见）/队列 API/命令行
- **分组规则**：同 ICC profile/同面料/同工艺/同机台参数的订单才能拼在一起
- **状态回传**（可选但建议）：RIP 接单/打印完成/切割完成/异常（用于你们回传 ERP）
