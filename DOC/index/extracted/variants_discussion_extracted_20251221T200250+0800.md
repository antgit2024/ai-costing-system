# 提炼：变体收口讨论（从 Cursor 导出记录提炼）

> 来源：`DOC/基础表单/前端 崩5 cursor_5.md`（导出时间：2025-12-21 20:02:50 GMT+8）  
> 提炼目的：把“可执行口径”沉淀为短文本，避免以后再读导出全文。

## 1) 关键共识（最稳的第一步）

- **基准清单 = 兜底**：任何条件不命中 → 以基准清单为准。
- **变体 = 例外（overlay）**：不直接改基准清单；用于动态生成最终 BOM。
- **扣库存/出库/核算唯一来源**：必须以 `POST /api/planner/bom/generate` 的 `final_material_lines` 快照为准（需落单并保留 trace）。

## 2) 变体能力收口（推荐默认形态）

为避免“太自由导致线上出错”，建议先把变体收口为：

- **动作**：只允许 `replace_self`
- **输出**：只允许 **1→1** 替换（不允许 1→N items）
- **单位约束**：仅允许替换到**相同计量单位**的物料（对账最稳）
- **条件**：先只开放 token（`contains_any/contains_all`）；尺寸条件先不开放或必须严格档位化

业务取舍：
- 不追求“一条规则整组替换（G001→G002）”
- 结构件增减（例如挂扣 2→3）优先由运营在**基准清单**兜底调整，变体只处理关键替换（例如 149→024）

## 3) 风险点（需要流程约束）

- **基准清单手工修改是默认生效**：会影响所有订单/规格的默认兜底，需要版本治理与发布流程。
- **孤儿规则**：如果删除了带变体的基准行，变体规则会悬空（不再触发）。需要 UI/流程提示与归档机制。
- **尺寸灰区**：99.9/100/100.1 易误触发，需要“整数边界 + 离散档位 + 固定解析口径”。

## 4) 建议运营/实施规范要点

- token 必须字典化/编码化（例如 `FRAME_024`），禁止自由输入近义词
- 启用前必须预演留痕（命中样例 + 不命中样例）
- 修改规则必须：先禁用 → 修改 → 预演通过 → 再启用
