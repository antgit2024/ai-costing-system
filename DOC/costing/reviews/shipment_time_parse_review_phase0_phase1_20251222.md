## 1. 当前项目是什么（仓库口径）

这是一个 **ERP 级“发货对账/扣库/成本核算”系统**：在“发货单导入”时（而非下单时）对每条发货明细进行 **规格解析（`spec_text → spec_hash`）**，并基于 **SKU→已发布标准版本（published standard version）绑定** 生成 **BOM 快照**；对未绑定/解析失败等异常写入 **异常队列**。所有结果 **可追溯、可重跑、快照不回写**。

## 2. 现状基线（已经落地、可依赖）

以 `DOC/agents/state.md` 为准，当前已落地并上线的主链路是：

- **发货导入与快照**：导入 xlsx → 标准化/幂等 → 生成 `spec_parse_snapshots` + `bom_snapshots` 或写入 `shipment_exception_queue`
- **幂等口径**：
  - 文件级：`file_hash=sha1(xlsx_bytes)`
  - 行级：`external_line_key_hash=sha1(shipment_no|sku_code|spec_text|qty|revenue_amount)`
- **只读前端对账页**：`/costing/shipments`（批次列表/异常队列/BOM 快照查询，已做“按 Excel 列展示”方向的可读性增强）

## 3. 痛点逐条回答（必须能落到治理/产品/接口）

### 3.1 为什么出现 `SKU_NOT_BOUND`？如何靠“SKU→已发布标准版本绑定”把异常消掉？

`SKU_NOT_BOUND` 的含义应固定为：**该 `sku_code` 在导入时无法解析到一个“可用且已发布的标准版本”**。常见根因分三类（建议异常 `message` 明确归因）：

- **未建立绑定**：`sku_code` 从未绑定任何标准版本（最常见）
- **绑定存在但不可用**：绑定指向的版本未发布/已禁用/已删除/未满足启用校验（“绑定表有记录但不能用于生产”）
- **绑定口径错误**：错误绑定到“模型/草稿/打样版本”，而非“已发布标准版本”（导致快照不可审计/不可回放）

把异常消掉的治理策略（建议 Phase0 即落地）：

- **发布门槛**：只允许绑定到 `published` 的 standard version（UI/后端双重校验）
- **批量绑定策略**（优先 Top 金额/Top 频次 SKU）：
  - 用异常队列导出 `sku_code` 清单 → 运营批量选择标准版本 → 一键写绑定
  - 允许“同货品编号/同店铺/同类目”的批量套用（需要一个可解释的分组键；最低限度先支持 `sku_code` 列表导入）
- **运营闭环**：异常队列里对 `SKU_NOT_BOUND` 给出“下一步动作”：
  - “去绑定”（跳转到绑定页/绑定抽屉）
  - “查看该 SKU 历史批次命中情况”（判断是否新 SKU / 还是绑定丢失）

> 评审结论：**异常不该被业务同事理解成“系统错误/解析失败”**，而应被理解成“主数据治理未完成”。因此文案必须从“错误码”升级为“缺少 SKU→已发布标准版本绑定（需发布后再绑定）”。

### 3.2 `spec_text` 不稳定：如何用 `spec_hash`、解析版本化与修订链路做到可追溯且不改历史？

建议将“规格不稳定”拆成两个层面治理：

- **计算层面（必须）**：对每条发货行保存原始 `spec_text`，并生成 `spec_hash`；解析快照写入 `parser_version`，BOM 快照 trace 里回填 `spec_hash + parser_version + bound_version_id`。  
  结论：**任何规则/词典/解析器升级都不回写历史快照**，只会影响“未来生成的快照”或“显式重跑生成的新快照”。

- **治理层面（可选）**：`DOC/基础表单/BOM系统优化完整方案_最终版.md` 主张在字段末尾嵌入稳定编码（如 `#S3V1F1`）以对抗营销文案变化。  
  评审建议：把“编码嵌入”定位为 **上游治理/兜底手段**，而不是本系统强依赖：
  - 强依赖会导致“未按规范埋码的历史订单全部不可算”，与当前“异常队列兜底 + 可重跑”策略冲突
  - 可作为 Phase1 的“可选增强”：当某些品类 `spec_text` 格式长期漂移时，允许通过埋码提升解析稳定性/减少词典维护成本

修订链路（Phase1 建议补齐）：

- 若同一业务行（同 `external_line_key_hash`）再次出现但 `spec_hash` 改变：**生成新的解析快照/新的 BOM 快照**，并标记为 `revision`（保留“旧→新”的父子关系），而不是覆盖旧记录。

### 3.3 发货导入幂等与重算：同文件幂等后，绑定补齐/规则更新后如何“重算/重试异常”？

当前幂等策略是正确方向，但需要补齐“重算语义”，避免业务误解“幂等=永远算不动”：

- **推荐口径**：
  - **幂等只保证“不重复写同一份结果”**（避免重复入库/重复扣库/重复统计）
  - **重算必须显式触发**，且产出 **新快照**（同一行可对应多次运行结果），并有“为什么重算”的可审计字段

Phase0 建议新增两种“重跑入口”（可先做最小 MVP）：

- **重试异常（Retry Exceptions）**：
  - 输入：`batch_id`（或 exception_ids）+ `only_unresolved=true`
  - 行为：仅对 `shipment_exception_queue` 中未解决的行重新跑“绑定→解析→BOM 快照”
  - 输出：新生成的 `bom_snapshot_id`/或更新异常为 resolved（但不删除异常记录）

- **再生成快照（Recompute Snapshots / Rerun Batch）**：
  - 输入：`batch_id` + `rerun_reason`（绑定补齐/词典升级/规则升级等）
  - 行为：创建一个新的 `import_batch`（或 `rerun_batch`）引用父 batch，逐行重跑并产出一组新快照
  - 约束：**不允许覆盖旧快照**，UI 查询允许按“父 batch / 子 batch”切换比对

### 3.4 UI/可读性：对账页面尽量按 Excel 结构展示，系统字段放抽屉/trace

方向正确：异常队列应以 Excel 字段为主（发货单号/货品条码/交易规格/数量/金额/店铺/完成时间…），系统字段（batch_id、shipment_line_id、spec_hash、bound_version_id、trace）放到抽屉。

对 `SKU_NOT_BOUND` 的 UI 建议（Phase0）：

- 异常行展示“业务原因 + 下一步动作”：  
  - 原因：`SKU 未绑定到已发布标准版本`  
  - 动作：`去绑定`（跳到 SKU 绑定页，或在抽屉里直接绑定）
- 抽屉里显示“绑定期望值”：例如“需要绑定到标准版本（published）”，并提示“绑定补齐后可一键重试本批异常”

## 4. Phase0 / Phase1 优先级建议（只列可落地项）

## 4.0 路线决策（与你当前目标对齐：先跑通主链）

你当前目标是“**发货单绑定到现有产品模型/标准版本**先跑通”。该选择在现系统下是最稳路径：

- **先主链**：发货导入 → SKU→已发布标准版本绑定 → spec_hash 解析 → BOM 快照/异常队列 → 可重试/可重跑（新快照、不回写历史）
- **后 30%**：在主链稳定后，再以“模型套模型 + 自动编码”扩展到多幅套装/非规则型等复杂产品（降低运营配置成本、提升解析稳定性）

因此，本评审稿将“模型套模型/编码”定位为 **Phase1 之后的扩展能力**（可选增强/治理手段），不作为当前主链的强依赖。

### 4.1 Phase0（强优先：立刻减异常、让业务跑通）

- **P0-1 绑定治理**：明确并固化“SKU→已发布标准版本绑定”的唯一口径（UI/后端都拦截未发布版本）
- **P0-2 批量绑定**：从异常队列导出/导入 `sku_code → version_id` 批量写绑定（先支持 CSV/Excel 导入即可）
- **P0-3 异常可解释**：`SKU_NOT_BOUND` 文案升级为“缺少 SKU→已发布标准版本绑定”，并在异常行提供“去绑定/重试异常”入口
- **P0-4 重试异常**：提供“按批次重试未解决异常”的最小 API/按钮（只生成新快照，不回写历史快照）
- **P0-5 Trace 展示收口**：系统字段统一进抽屉（`spec_hash/bound_version_id/parser_version/external_line_key_hash`），主表只留 Excel 口径字段

### 4.2 Phase1（增强：抗规格漂移、降低运营成本、提升可观测）

- **P1-1 解析版本化 + 修订链路**：对 `spec_hash` 变化/解析器升级产生的再运行建立 revision 关系（父子链路可查询/可比对）
- **P1-2 解析治理（词典/模板）**：把高频失败的 `spec_text` 模式沉淀为模板/词典；指标化监控解析成功率、兜底使用率
- **P1-3 可选“稳定编码嵌入”治理**：对极不稳定的品类引入埋码（`#...`），作为解析的优先信号；但不强制所有历史数据必须埋码
- **P1-4 重跑比对**：支持“父 batch vs rerun batch”的快照差异对比（用于验证规则升级效果与回归）

## 5. 风险与应对（评审必写）

- **风险：把绑定做成“模型级”而非“发布版本级”** → 造成快照不可回放  
  - **应对**：后端强校验 `version_kind=standard && published=true`
- **风险：幂等与重算语义混淆** → 业务误以为“补齐绑定也无法算”  
  - **应对**：UI 明确“重试异常/重跑批次”入口 + 审计字段 `rerun_reason`
- **风险：规格格式漂移导致解析失败** → 异常堆积  
  - **应对**：Phase1 建模板/词典与解析指标；“埋码”仅作为可选治理，不阻断主链路
