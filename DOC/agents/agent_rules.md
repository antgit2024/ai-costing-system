## Agent 统一规则（防慢/防崩/防丢上下文 — 2026-05-09 18:00 重大修订）

> 适用：@Planner / @Hub / @Frontend Agent / @Backend Agent / @Docs Agent / @Data Agent / @Ops Agent
> 目标：把"上下文"从聊天迁到仓库；任何新 Agent 10 分钟内可恢复工作。
>
> **2026-05-09 18:00 重大修订背景**：之前 §2「每轮只交付一个可验收产物（强制闭环）」+ task_distribution_standard.md §0.2「只改自己域内」+ §3.2「每轮 3 件强制」三条加在一起，把执行 Agent 锁成"小步频繁汇报"模式 → 交接 Token > 编码 Token 的形式主义。本次修订：(a) 区分**设计阶段（整体交付）** vs **执行阶段（小步迭代）**；(b) 给予执行 Agent **完整自主权限**；(c) 新增"交接成本 ≤ 编码成本"硬约束。

### 0) 只读工作集（禁止全仓扫描）

- **只允许读取**：`DOC/agents/workset.md` 列出的文件/目录（5–20 个）。
- 任何需要扩展阅读的内容：先更新 `workset.md`，再读文件。
- 例外：执行 Agent 在自己任务 scope 内可以读 scope 关联的所有代码（不需要逐个文件加 workset），但 scope 外仍受白名单约束。

### 1) 大文件"永不直喂"

- 禁止直接读取/粘贴超大导出/日志（例如 `DOC/index/前端崩4cursor_.md`、`DOC/agents/state.md` 3000+ 行）。
- 必须先用 grep/glob 检索目标段，或提炼到 `DOC/index/extracted/`。
- `DOC/agents/state.md`：用 grep 关键词搜索 ±50 行段落，禁止 `cat` / Read 全文。

### 2) **任务粒度区分（设计阶段 vs 执行阶段）— 2026-05-09 18:00 修订**

> **关键认知**：方案设计是"整体性产物"，强行拆成多轮零散汇报会让新 Agent 接力时只能看到碎片；项目执行是"渐进性交付"，可以分小步但不能频繁要求全局汇报。

#### 2.1 方案设计阶段（Hub Agent / Planner Agent 主导）

- **整体交付原则**：一份方案要落定就要完整落定（必读段 / 数据模型 / 接口契约 / 验收命令 / 与现有系统的关系都齐全），不要拆成"先写概要、再写表设计、再写接口"这种多轮汇报。
- **判定标准**：新 Agent 拿到方案文档**不需要回看历史聊天**就能开干，否则方案就是没写完。
- **多文档校准**：当一次升级涉及多份相关文档（如 Hub v1.3 同时联动总图 / 优先级规则 / 防忘表），允许在同一轮闭环里改 3~5 份文档，**这不算"跨文件风暴"**（详见 §3 修订）。

#### 2.2 项目执行阶段（Backend / Frontend / Docs / Ops Agent 主导）

- **大任务自主权**：尽量一个大任务（≥ 1 周工作量）由一个执行 Agent 自主完成，包括所有中间步骤的拆分、子 commit、调试。
- **不要每小步都回 Hub 汇报**：执行 Agent 在 scope 内拥有完整自主权（读写代码 / 跑测 / 调试 / 子 commit / 发起 PR），完成后才回 Hub 做归集汇总。
- **闭环判定**：以"用户能用 / 能验收"为闭环标志，不是以"代码改动行数 < 100"为标准。
- **里程碑可分**：demo / 上线 / 评审等大里程碑必须是完整闭环；中间过程不需要 Hub 干预。

### 3) 大 diff / 跨文件风暴的精确定义（2026-05-09 18:00 修订）

> 以前规则太死板，把"一致性升级"也当成了风暴。本次精确化定义。

#### 3.1 真正的"风暴"（必须避免）

- 在没有清晰主题的情况下，一次提交动几十个文件
- 顺手重构 unrelated 组件 / 顺手改 unrelated 配置
- 大规模重命名 / 大规模格式化（应该单独一次提交）

#### 3.2 不算"风暴"的合理跨文件改动（允许）

- **一致性升级**：如 Hub v1.3 升级时同步改总图 / 优先级规则 / 防忘表（强相关）
- **接口对齐**：后端改 API → 前端 service / types / 调用方一起改（同主题）
- **数据流端到端**：BFF → API → Service → Migration 一条线改（同主题）

判定标准：**所有改动必须有同一个主题，且新 Agent 看 commit message 就能理解为什么放一起**。

### 4) 统一恢复包（崩了也能继续）

每次进入一个新任务/新阶段，必须维护以下 4 个文件（短小、稳定）：

- `DOC/agents/state.md`：当前分支/当前改动点/未完成清单（≤15 行）+ 最近一次**已确认快照**路径
- `DOC/agents/commands.md`：一键复现命令（build/test/curl）
- `DOC/agents/known_issues.md`：已知坑/绕过
- `DOC/agents/workset.md`：允许读取的工作集清单

### 5) 输出限流（默认短结论 + 指向性引用）

- 默认只输出：结论、步骤、文件路径/函数名/行号。
- 日志/大表：只给"前 20 行 + 摘要 + 保存到的文件路径"。

### 6) 时间与时区口径（避免误回滚）

- 所有"今天/昨晚/几点"的口径统一用 **北京时间（GMT+8）**。
- 如果需要从导出文件恢复，以导出头部的 `GMT+8` 时间为准；不要凭感觉回退到更早版本。

### 7) 交接成本 ≤ 编码成本（硬约束 — 2026-05-09 18:00 新增）

> **背景**：用户 2026-05-09 17:45 明确指出"之前派活，形式大于实用，派活的交接记录的 Token 费用 > 实际写代码的费用"。这是规则失败，必须修正。

#### 7.1 硬指标

- **交接 Token 占比 ≤ 30%**：派单文档 + 任务汇报 + 验收 ceremony 加起来不能超过总 Token 30%；超过就说明任务粒度太碎，必须合并。
- **接力时间 ≤ 10 分钟**：新 Agent 拿到任务单 + 工作集 + 系统能力清单后，10 分钟内能开始动手。超过 10 分钟说明文档不够清晰或工作集太大。

#### 7.2 软原则

- **能放进 1 份方案的不要拆 2 份** — 比如 Hub v1.3 升级时，所有相关章节一次写完，不要"先写表设计、再写 API、再写 UI"。
- **能让执行 Agent 自主决定的不要在派单里规定** — 比如不要规定"先写 service 再写 router"，让 Agent 自己决定。
- **避免"为了流程而流程"** — 验收命令应该真的能验证东西，不是为了打卡。

#### 7.3 反模式（任何 Agent 看到必须立即纠正）

| 反模式 | 现象 | 修正方向 |
|---|---|---|
| 形式主义打勾 | 强制每轮跑 8 步检查 / 5 条硬规则勾完 | 减少到核心 3 步，其余作为软指引 |
| 派单 Token 爆炸 | 任务单 1000+ 行，描述 < 实际工作量 | 整合任务粒度，减少派单数量 |
| 频繁汇报中断 | 执行 Agent 每 30 分钟回 Hub 一次 | 给完整自主权，完成后才汇报 |
| 文档版本号风暴 | 11 份文档全部 v1.x → v2.x 联动升级 | 用"文档优先级规则"覆盖 + 关键文档定向升级（见 system_capability_inventory.md §12.2）|

### 8) 多 Agent 派活原则（task_distribution_standard.md 主导，本规则只提硬约束）

- 见 `DOC/agents/task_distribution_standard.md` §0.2 修订版"执行 Agent 完整自主权"
- 派活时优先选**大任务整体外包**，避免"加一个按钮 + 加一个字段"这种 30 分钟任务也走派单流程
