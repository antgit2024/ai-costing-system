## 标准模型：行级变体（Overlay）运营/实施规范（v0.1）

> 目的：让“变体规则”像 ERP 工程变更一样可控、可审计、可复现；避免自由度过高导致线上扣料/对账风险。
>
> 口径总原则：**基准清单 = 兜底**；**变体 = 例外**；订单/出库以最终 BOM 快照为准。

> 补充：本规范后续讨论的提炼件见 `DOC/index/extracted/variants_discussion_extracted_20251221T200250+0800.md`（避免读导出全文）。

### 1) 定义与边界（强制）

- **基准清单（version lines）**：标准版本的兜底配置。任何条件不命中 → 以基准清单为准。
- **变体规则（line-variants）**：针对某个 `base_line_id` 的例外规则（overlay），用于在满足条件时影响最终 BOM 生成。
- **最终 BOM（bom/generate）**：给订单出库/扣库存/成本核算的实际用料清单；必须可追溯到“基准清单 + 变体规则 + spec_text”。

### 2) 规则命名与备注（强制）

每条变体规则必须填写备注（notes），建议固定模板：

- **触发原因**：为什么要变体（例如：024 画框替换）
- **适用范围**：哪些规格/哪些订单会命中（例如：spec 含 token=024）
- **影响说明**：变体产生哪些物料变化（例如：149→024；挂扣由运营在基准清单手动替换为 3 号）
- **责任人/日期**：谁维护、何时生效
- **有效期（可选）**：临时规则必须写预计下线日期

### 3) token（关键词）规范（强制“字典化”）

- token 必须来自运营维护的**词典**（建议使用“编码 token”，如 `FRAME_024`、`HOOK_03`、`FRAMELESS`）。
- 禁止自由输入近义词混用（例如 “024/24号/24#” 不允许并存），必须归一为同一个 token。
- 词典变更必须记录：新增/废弃 token 的发布时间与迁移说明（避免历史规则失效）。

### 3.1) 强制“锚定模型”以避免跨模型误触发（强制）

背景：你们是“品类扩展型 + 物料复用”，同一面料/辅料可能同时用于抱枕/桌布/桌旗等不同模型。
如果只用 spec_text 的材质词/颜色词/编码（例如 `WB01176`）做匹配，很容易出现**跨模型误触发**。

#### 规则要求（从现在开始的新规则）

- **每条变体规则的条件必须包含 1 个锚定 token**（建议优先级从高到低）：
  - `MODEL:<三位模型码>`（例如 `MODEL:PI5`）
  - 或 `BOUND_VERSION:<标准版本ID>`
  - 或 `SKU:<货品条码>`
- 建议用 `spec_contains_all`（token(all)）来写锚定：保证“没锚定就不触发”。

#### 系统实现说明（无需运营改 spec_text）

- `spec/parse`（规格解析）仍保持“只从交易规格 spec_text 提取 tokens”的纯口径，用于审计/回放。
- `bom/generate`（BOM 预演/发货生成）在做变体匹配时，会**额外注入运行时上下文 tokens**（不要求出现在 spec_text）：
  - `MODEL:<model_code>`、`BOUND_VERSION:<version_id>`、`SKU:<sku_code>`
- 备用：若 spec_text 本身出现三位模型码（如 `PI5`/`A1B`），`spec/parse` 会额外输出 `MODEL:<code>` 作为辅助 token（用于排错/自动绑定候选），但这不是运营必须输入的字段。

### 4) 尺寸条件使用规范（允许，但必须“边界离散化”）

尺寸类条件容易出现灰区（99.9/100/100.1）与客服/工厂解释成本，因此允许使用，但必须遵守：

- **边界只能使用整数**：建议统一用整数毫米或整数厘米，不允许小数边界。
- **强制离散档位**：不要写 “99–101” 这种灰区范围；改为明确档位（例如：100 档 / 105 档 / 110 档）。
- **解析口径固定**：尺寸解析必须有统一策略（例如“向上取整到 1cm/5mm”或“四舍五入到 1cm”），并写入运营手册，禁止各人随意口径。
- **重叠必须可解释**：若两个规则边界重叠，必须通过“优先级 + stop_on_hit”明确决策，并在备注写清楚。

### 5) 上线前预演与留痕（强制）

每条变体规则上线前必须至少留存 2 个预演样例（可写在备注/台账）：

- **命中样例**：spec_text → tokens → 最终 BOM 关键行（至少编码/名称/数量）
- **不命中样例**：spec_text → tokens → 最终 BOM（应回落兜底清单）

### 6) 变更控制（强制）

- **启用/禁用**必须由指定角色执行（运营/实施负责人）。
- 修改规则（条件、items、动作）必须遵循流程：
  - 先禁用 → 修改 → 预演通过 → 再启用
- 临时规则必须设定清理机制（至少写有效期与责任人）。

### 7) 基准清单与变体的协作方式（推荐）

为避免“整组替换”误解导致风险，推荐采用：

- 变体规则只处理“关键替换”（例如：149 画框 → 024 画框）
- 其它结构件变更（例如：2 号挂扣 → 3 号挂扣）由运营在**基准清单**中直接调整并保存为版本兜底
- 若后续需要真正“组级替换（G001→G002）”，应由后端引入 bundle_key/group_id 语义并加强校验（另开迭代）

### 7.1) 推荐默认形态（最稳第一步：同计量单位 1→1 平替）

> 默认建议先把系统收口为“可审计、可对账”的最小形态，再逐步放开复杂动作。

- **动作**：默认只允许 `replace_self`（替换本行）
- **输出**：只允许 **1→1**（不允许 1→N items，不允许结构性增删）
- **单位**：只允许替换为 **相同计量单位** 的物料（避免出库/对账争议）
- **条件**：先只用 token（`spec_contains_any/spec_contains_all`）；尺寸条件若要开放，必须严格按“整数边界 + 离散档位 + 固定解析口径”

业务取舍（必须接受）：
- 不追求“一条规则整组替换（G001→G002）”
- 挂扣等结构件增减优先由运营在**基准清单**兜底调整；变体只做关键替换（例如 149→024）

### 7.2) 一个物料（base_line_id）建议多少个条件/规则？

为防“规则爆炸”，建议运营侧执行上限：

- **每个 base_line_id**：启用规则建议 **≤ 3 条**（极限不超过 5 条）
- **每条规则的 token 条件**：
  - `contains_any` 建议 token 数 **≤ 5**
  - `contains_all` 建议 token 数 **≤ 3**（越多越难解释与维护）

超过上限时，必须先做合并/重构（例如将 token 归并为更高层编码 token，或把默认行为沉淀到基准清单）。

### 8) 库存/出库/成本核算口径（强制）

- **扣库存/出库/成本核算必须以最终 BOM 快照为准**：
  - 每次订单/出库生成时，必须调用 `bom/generate` 得到 `final_material_lines`，并把结果（含 trace）落单快照
  - 基准清单与变体规则仅作为“生成依据”，不得直接作为扣减依据（避免“界面看到的 ≠ 实际扣的”）
