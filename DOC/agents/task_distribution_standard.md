# Hub Agent 派单体系：跨项目标准说明（可复用）

> 适用：任何多 Agent / 多角色协作的代码仓库
> 目标：把"上下文"从聊天搬到仓库，避免全仓扫描/大文件直读/大 diff 导致变慢与崩溃；让新项目、新 Agent 能 10 分钟内恢复工作。
>
> **2026-05-09 18:00 重大修订**：基于"派活的 Token 费用 > 实际写代码的费用"教训，本次将 §0.2 / §2 / §3 全面重写：
> - 执行 Agent 拥有**完整自主权限**，Hub 不再控制中间步骤
> - 派单优先**大任务整体外包**（≥ 1 周工作量），避免微任务派单
> - "一轮一闭环"原则**仅适用于项目执行的里程碑**，不适用于方案设计

## 0. 角色与边界（必须遵守 — 2026-05-09 18:00 修订）

### 0.1 Hub Agent（= 新 Planner）

**只做：协调/接力/规则执行/派单/跨域同步/归集汇总**，原则上不直接写业务代码（允许写文档、写任务单、维护恢复包）。

Hub Agent 负责：
- 维护恢复包与只读工作集（见第 1 节）
- 将需求拆成**大任务**的任务单（见第 3 节模板，注意：**不是小步任务**）
- 负责跨域互联：
  - Backend 接口变化 → 同步到前端索引（`services/types`）与文档口径
  - Docs 口径变化 → 同步到 UI 规格/指南，并提醒前端调整
- **归集汇总**执行 Agent 的成果，更新 `task_log.md` / `state.md`
- 控制 scope：禁止全仓扫描；但允许执行 Agent 在 scope 内自由读写（见 §0.2）

Hub Agent **不做**：
- ❌ 干预执行 Agent 的中间步骤（不要"先写 service 再写 router"这种规定）
- ❌ 要求执行 Agent 频繁汇报（除非任务卡死或 scope 需要扩）
- ❌ 把大任务拆成 5 份小任务单（应该一份大任务单交给一个 Agent 自主完成）

### 0.2 执行 Agent（Frontend / Backend / Docs / Ops / Data）— **完整自主权**

**关键修订**：执行 Agent 在任务单的 scope 范围内拥有**完整自主权限**，Hub 不再控制具体步骤。

执行 Agent 拥有的**完整权限**：
- ✅ 在 scope 内自由读写代码、跑测、调试、查日志
- ✅ 自主决定中间步骤的拆分（先写哪个文件、要不要重构、子 commit 怎么分）
- ✅ 自主管理子 commit / 子 PR（一个主题一个 commit 或合并成一个 PR 都可以）
- ✅ 自主调用 Shell / Grep / Read / 子 agent / MCP 等工具，不需要请示 Hub
- ✅ 在 scope 内可以读 scope 关联的所有代码（不需要逐个文件加 workset）
- ✅ 完成后做归集，回填 `state.md` + `task_log.md`，再回 Hub 报告

执行 Agent 的**唯一硬约束**：
- 不能改 scope **外**的文件（要扩 scope 必须先回 Hub 改 workset）
- 任务交付时必须满足任务单的"完成标准"（详见 §3.1）
- 完成后必须回填恢复包（`state.md` + `task_log.md`）

> **说明**：如果项目需要，可增加 `@Ops Agent`（部署/迁移/重启/网关）、`@Data Agent`（数据治理）。仍由 Hub Agent 派单，但都享有 §0.2 的完整自主权。

### 0.3 何时执行 Agent 必须回 Hub（仅 3 种情况）

> 默认执行 Agent 不需要中途汇报。只有以下 3 种情况必须立即回 Hub：

1. **scope 不够**：发现需要改 scope 外的文件，必须先回 Hub 申请扩 workset
2. **架构冲突**：发现任务单的设计与现有系统冲突（如表已存在、接口已改），必须回 Hub 同步设计
3. **完全卡死**：尝试 ≥ 3 种方案后仍无法推进，回 Hub 求助

**除此 3 种情况外**：执行 Agent 应自主推进，避免无意义的进度汇报。

## 1. 必备文件与目录（新项目必须先建立）

> 这些文件是“唯一上下文载体”。没有它们，任何协作都会退化成聊天堆上下文。

### 1.1 恢复包（必须维护，短小稳定）

放在 `DOC/agents/`：
- `workset.md`：**只读工作集**白名单（允许读取的文件/目录列表）
- `state.md`：当前状态（分支/本轮产物/下一步/验收命令/北京时间）
- `commands.md`：可执行命令清单（build/test/curl/部署）
- `known_issues.md`：已知坑与绕过方式
- `task_log.md`：变更记录（表格，一行一事）

### 1.2 任务单目录（强制）

放在 `DOC/agents/briefings/`：
- 每个闭环任务一份文件，例如：
  - `backend_xxx_mvp.md`
  - `frontend_xxx_mvp.md`
  - `docs_xxx_update.md`

### 1.3 大文件提炼目录（强制）

放在 `DOC/index/extracted/`：
- 任何超大导出/日志/长文禁止直读
- 必须先提炼出 Top-N 片段到该目录，并在 `state.md` 记录提炼件路径

## 2. 统一强制规则（2026-05-09 18:00 修订 — 减少形式主义）

1) **只读工作集**：只允许读取 `DOC/agents/workset.md` 列出的文件/目录；需要扩展阅读先改 `workset.md` 再读。执行 Agent 在 scope 内可自由读写关联代码。
2) **大文件不直读**：超大导出/日志必须先 grep 检索或提炼到 `DOC/index/extracted/`。
3) **任务粒度区分**（核心修订，替代旧"一轮一个闭环"硬规则）：
   - **方案设计阶段**（Hub 主导）：方案要整体落定，禁止拆成多轮零散汇报。一份方案要满足"新 Agent 不需要回看历史聊天就能开干"。
   - **项目执行阶段**（执行 Agent 主导）：尽量一个大任务（≥ 1 周工作量）一个 Agent 自主完成，**不要**把"加一个按钮 + 加一个字段"这种拆成 5 个任务单。闭环以"用户能用 / 能验收"为标志，不是"代码改动 < 100 行"。
4) **可恢复包必须维护**：任务交付后必须更新 `state/task_log/known_issues/workset`（按需），保证崩了也能继续。
5) **北京时间口径**：所有时间以北京时间（GMT+8）为准。
6) **验收门槛**：前端任务交付时必须跑 `npm -C frontend run build`；后端/文档按 `commands.md` 执行。中间过程的验收由执行 Agent 自主决定。
7) **交接成本 ≤ 编码成本**（新增硬约束）：派单文档 + 任务汇报 + 验收 ceremony 加起来不能超过总 Token 30%；超过就说明任务粒度太碎，必须合并。详见 `agent_rules.md §7`。

## 3. Hub Agent 派单模板（2026-05-09 18:00 修订 — 优先大任务）

> 每次派单必须首行声明身份（只选一个）：
> `你是 @Frontend Agent` / `你是 @Backend Agent` / `你是 @Docs Agent` / `你是 @Ops Agent` / `你是 @Data Agent`
>
> **派单总原则**：优先选大任务整体外包，避免"加一个按钮"这种 30 分钟任务也走完整派单流程。以下模板适用于 ≥ 1 天工作量的任务；30 分钟以内的任务直接对话内交代即可，不强制走任务单。

### 3.1 大任务任务单模板（写入 `DOC/agents/briefings/*.md`）

- **任务名**：<域>-<模块>-<一句话目标>
- **预估工作量**：<人天 / 周>（< 1 天的任务请合并）
- **任务范围**：<文件/目录清单 + 关联系统>（执行 Agent 在此 scope 内有完整自主权）
- **完成标准（≤ 5 条，可观察可验收）**：
  - 例：`/api/xxx` 接口返回正确结构
  - 例：前端 xxx 页面用户可以走完 yyy 流程
  - 例：跑通 `pytest backend/tests/xxx -q`
- **验收命令（执行 Agent 自主选 1~3 条最能证明完成的）**：
  - 推荐从 `DOC/agents/commands.md` 选
  - 不强制 1 条；不强制 0 退出码（如有 known issue 可以接受 warning）
- **依赖契约**（如有跨域影响必填）：
  - API：<method + path + request/response 关键字段>
  - 类型/枚举：<字段名口径、可选值>
  - 文档口径：<UI spec/requirements 引用路径>
- **必读上下文**（替代旧"workset"逐文件列表，让 Agent 一次性掌握全局）：
  - `DOC/costing/handovers/system_capability_inventory.md`（全系统能力快照，必读）
  - 与本任务相关的 1~2 份蓝图文档
  - 相关代码入口（router / service / page 主文件路径）
- **完成后归集要求**：
  - `DOC/agents/state.md`：更新本任务产物/下一阶段/北京时间日期
  - `DOC/agents/task_log.md`：追加一行（日期/模块/角色/任务/结论/待办）
  - 如产出快照/提炼件：写入 `DOC/index/extracted/` 并在 `state.md` 记录路径

### 3.2 派单统一尾注（修订 — "任务交付时" 而非"每小步"）

【任务交付时必须完成 3 件事 — 中间过程不强制】
你完成本**整个任务**（不是每小步）后，交付前必须做 3 件事，否则视为未交付：
1) 更新恢复包（必须）：同步更新 `DOC/agents/state.md`（写清本任务产物 + 下一阶段 + 北京时间日期）、必要时更新 `DOC/agents/known_issues.md` / `DOC/agents/commands.md` / `DOC/agents/workset.md`。
2) 硬验收（必须）：前端跑 `npm -C frontend run build`；后端/文档按 `DOC/agents/commands.md` 的命令验收（你自己选最能证明任务完成的命令）。
3) Git 落地（必须）：把你改动的代码 + 对应 `DOC/agents/*` 一起 `git add`，并提交（可以一次大 commit 或多个子 commit，由你自主决定，**避免微 commit 风暴**）。

【中间过程 — 你拥有完整自主权】
- 你可以自由调用 Shell / Grep / Read / 子 agent / MCP 等工具
- 你可以自主决定先写哪个文件、要不要重构、子 commit 怎么分
- 你不需要每 30 分钟回 Hub 汇报进度
- 仅以下 3 种情况必须立即回 Hub（详见 §0.3）：
  (a) 需要改 scope 外的文件 → 申请扩 workset
  (b) 发现任务单设计与现有系统冲突 → 同步设计
  (c) 尝试 ≥ 3 种方案后仍无法推进 → 求助

### 3.3 微任务（< 1 天工作量）的派活方式

> 不需要走完整任务单流程。

- 直接在对话里交代：目标 + scope + 完成标准（3 行内说清）
- 完成后只更新 `task_log.md` 一行即可（不强制更新 state.md / commands.md）
- 适用场景：调一个 bug、改一个文案、加一个字段、写一份小补丁文档

## 4. 新项目落地步骤（最小可用）

1) 在仓库建立上述目录与文件：`DOC/agents/*`、`DOC/agents/briefings/`、`DOC/index/extracted/`
2) 在 `workset.md` 写入本轮允许读取的最小文件集合（5–20 个）
3) 在 `commands.md` 写入前端/后端的"候选验收命令清单"（不是"唯一"）
4) Hub Agent 产出第一份**大任务**任务单（briefing），按 §3.1 模板派单
5) 执行 Agent 在 scope 内自主推进，完成后回填 `state/task_log` 并提交

## 5. 验收（本标准说明自身的验收方式）

建议在 `state.md` 里给出以下验收命令之一（择一即可）：
