# 吉客云货品同步接口订购建议

作者：**Manus AI**  
日期：2026-05-13

## 结论先行

我已经按官方接口文档的数据源读取并批量拉取了相关目录下的接口详情，本次不是只看截图判断。对于你提出的两个核心功能，建议订购和接入的接口应分为**ERP 货品主档读写**、**在线商品档案读写**、**发货确认逆向**三类。不能把“商品档案 item”和“ERP 货品 sku/goods”混为一个接口，否则后面很容易出现字段不全、写错对象或无法覆盖未同步货品的问题。

| 业务目标 | 结论 | 必须关注的接口 |
|---|---|---|
| 从 ERP 拉取 100 万级货品，保证字段尽量完整 | 以 `erp.storage.goodslist` 为主，因为它返回字段最多，官方字段数为请求 23、返回 168，并包含 `goodsField1-50`、`skuField1-30`、`skuCode`、`goodsAttr`、主条码、停用/删除状态等。 | `erp.storage.goodslist` |
| 按条件筛选 ERP 货品，尤其只更新未同步货品或特定编码货品 | 用 `erp-goods.goods.sku.search` 做条件筛选，但它返回字段少，不能替代完整同步。 | `erp-goods.goods.sku.search` |
| 将我们系统里更真实的属性、商家编码/外部编码、自定义字段反写 ERP 货品 | 用 `erp.goods.skuimportbatch`，官方说明它既可批量创建，也可在货品存在时更新；但核心匹配依据是 `outSkuCode`。 | `erp.goods.skuimportbatch` |
| 获取自定义字段中文含义，避免 `goodsField1` 这种字段后续无法解释 | 必须用 `erp.goods.customfield` 建字段字典。这个接口不需订购但要接入。 | `erp.goods.customfield` |
| 如果你们说的“在线货品信息”指吉客云“商品库/商品档案”而不是 ERP 货品主档 | 需要另接商品档案接口；读用 `erp-goods-online.item.details`，写用 `erp-goods-online.item.batchupdateitem`。 | `erp-goods-online.item.details`、`erp-goods-online.item.batchupdateitem` |
| 发货确认逆向 | 如果业务是 WMS/外部仓把实际发货结果回传吉客云，优先看 `wms.order.basicbatchconfirmsync`；如果是订单发货确认信息回传外部系统，则 `oms.trade.confirm` 的官方说明方向不是“写 ERP 货品主档”。 | `wms.order.basicbatchconfirmsync`、`oms.trade.confirm` |

> 关键判断：**ERP 货品主档字段的完整同步，不能只依赖 `erp-goods.goods.sku.search`，必须订购并使用 `erp.storage.goodslist` 作为主读取接口；反向写 ERP 货品主档，必须订购并使用 `erp.goods.skuimportbatch`。**

## 一、我确认需要订购的接口

| 优先级 | 接口 | 官方名称 | 是否需订购 | 为什么需要 |
|---:|---|---|---:|---|
| P0 | `erp.storage.goodslist` | 分页查询货品信息 | 是 | 这是 ERP 货品主档最适合作为“全字段同步”的读取接口。官方返回 168 个字段，覆盖货品基础资料、规格、`goodsField1-50`、`skuField1-30`、`skuCode` 外部货品编码、`goodsAttr` 货品属性、主条码、停用和删除状态等。 |
| P0 | `erp.goods.skuimportbatch` | 批量创建货品 | 是 | 这是对 ERP 货品主档进行创建/更新的核心写入接口。官方说明 `outSkuCode` 是两个系统之间货品匹配关系的唯一依据；如果货品没有 `outSkuCode`，无法用该接口更新货品。接口请求字段 147 个，覆盖货品属性、外部编码、货品自定义字段 1-50、规格自定义字段 1-30、图片、描述、默认供应商、重量体积、批次/序列号/有效期等。 |
| P0 | `erp.goods.customfield` | 获取货品自定义字段说明 | 否 | 必须接入，用来把 `goodsField1-50`、`skuField1-30` 这类字段映射成 ERP 实际配置的中文含义、类型和长度，否则后面无法保证字段解释一致。 |
| P1 | `erp-goods.goods.sku.search` | 条件查询货品 | 是 | 适合做条件筛选、按修改时间增量查询、按 `goodsNos`、`skuBarcodes`、`skuNos`、`skuCodes`、部分自定义字段过滤。但它返回字段只有 33 个，官方也只列到 `goodsField1/2/29/30`、`skuField1/2/29/30` 等摘要字段，所以不能作为全字段主同步。 |
| P1 | `wms.order.basicbatchconfirmsync` | 批量发货确认（逆向）-同步 | 否 | 如果你们系统掌握实际出库、批次、SN、包裹、物流、实发数量等真实发货结果，要反向确认给吉客云，这个接口字段更完整，包含出库单、货主、仓库、商品明细、`outSkuCode`、批次、SN、包裹物流等。 |
| P2 | `erp-goods-online.item.details` | 获取商品库商品信息 | 是 | 只在你们要同步“商品库/商品档案 item”时需要。它能读商品标题、商品货号、商品编码、品牌、图片、PC/WAP详情、销售属性、规格、规格条码、规格编号等，但官方明确它不能获取从网店下载的商品信息。 |
| P2 | `erp-goods-online.item.batchupdateitem` | 批量更新商品档案 | 是 | 只在你们要更新“商品档案 item”时需要。它不是 ERP 货品主档写入接口。官方提供 `updateType=1` 全量覆盖和 `updateType=2` 增量更新，但每次最多 50 个不重复 `itemCode`，且只更新未停用、未删除、审核状态非待审核的商品。 |

## 二、两个业务功能如何落地

### 功能 1：我们系统的真实信息反向写入 ERP

这个需求应拆成两条线。第一条是**真实发货结果反向确认**，它解决的是订单/出库/物流/批次/SN/实发数量；第二条是**货品主档字段反写**，它解决的是属性、外部编码、商家编码、自定义字段等货品资料。官方文档里这两类接口不是同一个。

| 子目标 | 建议接口 | 关键字段或规则 | 判断 |
|---|---|---|---|
| 真实出库结果、实发数量、批次、SN、物流回传 | `wms.order.basicbatchconfirmsync` | `results-goods-outSkuCode`、`actualqty`、`batchs`、`snlist`、`packagelist`、`expresscode` | 适合做发货确认逆向，但不是货品主档字段更新接口。 |
| 普通订单发货确认信息 | `oms.trade.confirm` | `order-tradeNo`、`goods-goodsNo`、`skuBarcode`、`sendCount`、`packages-logisticNo` | 官方说明是“将订单发货确认信息回传给外部系统”，方向上不等同于“写 ERP 货品主档”。 |
| 属性、外部编码/商家编码、自定义字段反写 ERP 货品 | `erp.goods.skuimportbatch` | `outSkuCode`、`goodsAttr`、`goodsField1-50`、`skuField1-30`、`skuNo`、`skuBarcode`、`mainBarcode` | 这是货品主档写入核心接口。必须先保证每个规格有稳定 `outSkuCode`。 |

因此，如果你们希望“发货信息里最真实的商家编码、属性、自定义字段自动反向写入 ERP”，不能只接发货确认接口。正确做法是：发货链路产生/校验真实字段后，由系统映射到 ERP 货品字段，再调用 `erp.goods.skuimportbatch` 更新货品主档；发货确认本身则调用发货确认逆向接口。

### 功能 2：未同步 100 万货品时，按条件筛选 ERP 货品并写入部分字段

这个需求应采用“筛选接口 + 完整详情接口 + 写入接口”的组合。`erp-goods.goods.sku.search` 适合先按条件找目标货品，但不能保证所有字段都返回；`erp.storage.goodslist` 返回字段更完整，应作为全量同步和详情补齐的主接口；最终写回仍然用 `erp.goods.skuimportbatch`。

| 步骤 | 接口 | 说明 |
|---|---|---|
| 首次全量或准全量同步 | `erp.storage.goodslist` | 官方说明首次传 `maxSkuId=0`，之后取上次返回的最大 `skuId`，不用传统翻页逻辑。建议用它建立本地完整货品索引。 |
| 日常增量 | `erp.storage.goodslist` 或 `erp-goods.goods.sku.search` | 两个接口都支持货品/规格修改时间条件。若要字段完整，以 `erp.storage.goodslist` 为准；若只是筛选目标，可用 `erp-goods.goods.sku.search`。 |
| 条件筛选未同步货品 | `erp-goods.goods.sku.search` | 支持 `goodsNos`、`skuBarcodes`、`skuNos`、`skuCodes`、创建时间、货品/规格修改时间、自定义字段条件等。 |
| 补齐完整字段 | `erp.storage.goodslist` | 对筛出的 `goodsNo`、`skuBarcode`、`skuCodes` 再查询完整字段，避免只拿到 33 个字段导致后续缺字段。 |
| 写入部分字段 | `erp.goods.skuimportbatch` | 传要更新的字段；但要严格用 `outSkuCode` 作为匹配依据，并控制单次最多 200 个货品。 |

## 三、必须同步和保存的字段范围

为了避免后续发现功能要用但字段没加，本地库不要只存当前页面展示字段。建议按 ERP 货品主档维度至少保留以下字段组。

| 字段组 | 来源接口 | 说明 |
|---|---|---|
| 主键和匹配字段 | `erp.storage.goodslist`、`erp.goods.skuimportbatch` | `goodsId`、`skuId`、`goodsNo`、`skuNo`、`skuCode/outSkuCode`、`skuBarcode`、`mainBarcode`。其中写入时 `outSkuCode` 是关键匹配依据。 |
| 货品基础信息 | `erp.storage.goodslist` | 货品名称、英文名、别名、分类、品牌、单位、备注、主图、规格图、长宽高、重量、体积。 |
| 货品属性和业务标识 | `erp.storage.goodslist`、`erp.goods.skuimportbatch` | `goodsAttr`，以及成品、半成品、原料、包装材料、辅料、资产、耗材、服务、设备、备件、费用等枚举含义。 |
| 自定义字段 | `erp.storage.goodslist`、`erp.goods.customfield`、`erp.goods.skuimportbatch` | 货品自定义字段 `goodsField1-50`，规格自定义字段 `skuField1-30`，并保存 `erp.goods.customfield` 返回的字段英文名、中文名、类型、长度、说明。 |
| 状态字段 | `erp.storage.goodslist` | 是否停用、规格是否停用、是否删除、是否组合装、是否批次管理、是否序列号管理、是否有效期管理等。 |
| 供应商和仓库相关字段 | `erp.storage.goodslist`、`erp.goods.skuimportbatch` | 默认供应商、存放仓库、货主、委外仓相关字段。 |
| 图片与详情 | `erp.goods.skuimportbatch`、必要时商品档案接口 | 货品主图、左右上下图、素材图、商品视频、规格主图、货品描述。 |

## 四、为什么 CORS 不行

CORS 不行是正常现象，原因不是接口不能调用，而是**开放平台 API 不应由浏览器前端直接调用**。吉客云开放平台接口通常需要应用凭证、签名、授权上下文等敏感信息；如果直接在浏览器里调用，不仅会遇到跨域策略拦截，而且会把密钥和签名逻辑暴露给用户端。正确架构应是：浏览器前端调用你们自己的后端；你们后端保存 appKey/secret/token，完成签名、限流、重试、日志、幂等和字段映射后，再请求吉客云开放平台。

| 错误做法 | 正确做法 |
|---|---|
| 前端页面直接请求 `open.jackyun.com` API，期望对方放开 CORS | 前端请求你们自己的服务端 API，由服务端请求吉客云开放平台 |
| 在前端保存 appSecret/token | 密钥只放服务端或密钥管理系统 |
| 浏览器直接批量同步 100 万货品 | 后端队列/定时任务分批同步，记录游标 `maxSkuId/lastMaxId` 和失败重试 |
| 前端直接拼接字段写 ERP | 后端做字段白名单、字段映射、幂等校验和审计日志 |

## 五、我认为不能选错的点

第一，`erp-goods.goods.sku.search` 名字叫“条件查询货品”，但返回字段只有 33 个，适合筛选，不适合完整同步。完整同步应以 `erp.storage.goodslist` 为准。

第二，`erp.goods.skuimportbatch` 名字叫“批量创建货品”，但官方说明中明确包含“如果存在则更新”的语义，并强调 `outSkuCode` 是两个系统货品匹配关系的唯一依据。因此它是你们做 ERP 货品主档反写的核心接口。

第三，`erp-goods-online.item.batchupdateitem` 更新的是“商品档案”，不是 ERP 货品主档。只有当你们要维护吉客云商品库/商品档案时才订购它；如果目标是 ERP 货品主档，不应拿它替代 `erp.goods.skuimportbatch`。

第四，`erp-goods-online.item.details` 官方明确不能获取从网店下载的商品信息。因此，如果你们所谓“在线货品信息”实际是网店下载商品，必须进一步确认吉客云是否另有店铺商品/线上商品读取接口，否则这个接口会漏数据。

## 六、建议的最小订购清单

| 套餐 | 必选接口 |
|---|---|
| ERP 货品主档同步最小集 | `erp.storage.goodslist`、`erp.goods.skuimportbatch`、`erp-goods.goods.sku.search`、`erp.goods.customfield` |
| 如果要接真实发货逆向 | 在上面基础上加 `wms.order.basicbatchconfirmsync`，并确认你们业务单据类型是否匹配 |
| 如果还要维护商品库/商品档案 | 在上面基础上加 `erp-goods-online.item.details`、`erp-goods-online.item.batchupdateitem` |

## 七、需要你们向吉客云或实施顾问确认的事项

| 待确认问题 | 为什么重要 |
|---|---|
| 你们说的“商家编码”在吉客云里究竟对应 `outSkuCode`、`skuCode`、`skuNo`、`itemCode` 还是平台侧商家编码字段 | 这些字段属于不同对象，写错会导致匹配失败或覆盖错商品。 |
| ERP 里所有货品规格是否已经有稳定 `outSkuCode` | 官方说明没有 `outSkuCode` 无法用 `erp.goods.skuimportbatch` 更新。 |
| 你们的“在线货品信息”是否来自吉客云商品库，还是从网店下载的商品 | `erp-goods-online.item.details` 官方明确不支持获取网店下载商品。 |
| 哪些自定义字段是货品级，哪些是规格级 | 货品级是 `goodsField1-50`，规格级是 `skuField1-30`，必须用 `erp.goods.customfield` 建字典并在本地保存。 |
| 发货逆向是写吉客云 ERP/WMS，还是吉客云回传你们外部系统 | `wms.order.basicbatchconfirmsync` 与 `oms.trade.confirm` 的方向和字段范围不同，不能混用。 |
